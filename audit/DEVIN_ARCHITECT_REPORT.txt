SECTION 1: EXECUTIVE SUMMARY
================================================================================

This report documents the complete static dissection of the upstream BlissOS
16.9.7 ISO and its alignment with the REMBO-Bliss-os Sovereign Edition
architecture. The analysis covers:

  - Full boot chain tracing from GRUB/ISOLINUX → Linux kernel → initrd init
    script → Android init → Zygote → SystemServer
  - ISO filesystem structure (ISO9660 → EROFS → ext4 system.img)
  - Identification of injection points for REMBO_SIDE_PATCH scripts via USB
  - Complete OverlayFS architecture for system file overrides
  - Alignment verification against the sovereign-edition-v1 branch

METHODOLOGY: Direct ISO extraction using 7z and cpio. No live boot simulation
was performed (KVM unavailable in audit environment). All findings are based
on static analysis of actual ISO contents.

SECTION 5: REMBO_SIDE_PATCH INTEGRATION VIA USB ROOT
================================================================================

ANALYSIS: Where the system can accept an external REMBO_SIDE_PATCH script
via USB root.

--- 5.1 Primary Injection Point: initrd /src/scripts/ ---

The initrd init script (line 391) sources all scripts from two directories:

    for s in `ls /scripts/* /src/scripts/*`; do
        test -e "$s" && source $s
    done

Where /src is a symlink to /mnt/$SRC (the root of the boot device).

INJECTION METHOD:
  1. Place REMBO_SIDE_PATCH script at: <USB_DRIVE>/scripts/rembo-side-patch.sh
  2. The script will be automatically sourced during Phase 2 of boot
  3. At this point, the Android filesystem is already mounted at /android
  4. The script has full root access to modify /android/system/* before
     Android init takes over

SCRIPT NAMING CONVENTION:
  Scripts are sourced in `ls` order (alphabetical). To ensure REMBO patches
  run AFTER default scripts (0-auto-detect, 1-install, 2-mount, 3-tslib),
  name the script with a high prefix:
    scripts/9-rembo-side-patch

EXECUTION CONTEXT:
  - Shell: busybox sh (ash)
  - User: root (UID 0)
  - Available: mount, ln, cp, cat, sed, awk, chmod, chown
  - Android FS: mounted at /android/system (read-only loop mount)
  - Boot device: mounted at /mnt (can be remounted rw)

--- 5.2 Secondary Injection Point: Android init.d Scripts ---

After switch_root, if the REMBO build includes an init.d service, scripts
in /system/etc/init.d/ can execute with root privileges. However, this
requires the scripts to already be inside the system image.

--- 5.3 Tertiary Injection Point: Sentinel Daemon ---

The existing rembo-sentinel.sh daemon already implements an OverlayFS-based
update mechanism that fetches packages from GitHub. This can be extended to
accept packages from a USB-mounted path:

    USB_PATCH_DIR="/mnt/usb/rembo-patches"
    if [ -d "$USB_PATCH_DIR" ]; then
        for patch in "$USB_PATCH_DIR"/*.zip; do
            apply_overlay_update "$patch" "$(sha256sum $patch | cut -d' ' -f1)" \
                "$(basename $patch .zip)"
        done
    fi

--- 5.4 Recommended REMBO_SIDE_PATCH Script Template ---

#!/system/bin/sh
# REMBO_SIDE_PATCH — USB Root Sidecar Script
# Location: <USB_ROOT>/scripts/9-rembo-side-patch
# Execution: Auto-sourced by initrd /init during Phase 2

PATCH_LOG="/tmp/rembo-side-patch.log"
log_patch() { echo "[SIDE-PATCH] $*" >> "$PATCH_LOG"; }

log_patch "=== REMBO Side-Patch Initializing ==="
log_patch "Boot device: /mnt/$SRC"
log_patch "Android FS: /android/system"

# --- Sovereign GRUB Parameters Verification ---
for param in VULKAN HWACCEL HWC GRALLOC; do
    eval val=\$$param
    log_patch "Boot param $param=$val"

# --- Inject Sovereign build.prop overrides ---
if [ -f /mnt/$SRC/rembo/sovereign_build.prop ]; then
    log_patch "Injecting Sovereign build.prop overrides..."
    cat /mnt/$SRC/rembo/sovereign_build.prop >> /android/system/build.prop
fi

# --- Inject Sovereign init scripts ---
if [ -f /mnt/$SRC/rembo/rembo-sovereign-init.sh ]; then
    log_patch "Copying Sovereign init script..."
    cp /mnt/$SRC/rembo/rembo-sovereign-init.sh \
       /android/system/bin/rembo-sovereign-init.sh
    chmod 755 /android/system/bin/rembo-sovereign-init.sh
fi

# --- Inject Sentinel daemon ---
if [ -f /mnt/$SRC/rembo/rembo-sentinel.sh ]; then
    log_patch "Copying Sentinel daemon..."
    cp /mnt/$SRC/rembo/rembo-sentinel.sh \
       /android/system/bin/rembo-sentinel.sh
    chmod 755 /android/system/bin/rembo-sentinel.sh
fi

# --- Inject GPU firmware if present on USB ---
if [ -d /mnt/$SRC/rembo/firmware/nvidia ]; then
    log_patch "Injecting NVIDIA firmware from USB..."
    cp -r /mnt/$SRC/rembo/firmware/nvidia/* \
       /android/system/lib/firmware/nvidia/
fi

log_patch "=== REMBO Side-Patch Complete ==="

SECTION 6: OVERLAYFS SOVEREIGN MAP — SYSTEM FILE OVERRIDE ARCHITECTURE
================================================================================

--- 6.1 OverlayFS Fundamentals ---

OverlayFS is a union filesystem that layers a read-write "upper" directory
on top of a read-only "lower" directory, presenting a unified view:

    mount -t overlay overlay \
        -o lowerdir=/system,upperdir=/data/overlay/upper,workdir=/data/overlay/work \
        /system

After this mount:
  - Reading a file: first checks upper/, then falls back to lower/
  - Writing a file: copy-on-write to upper/ (original in lower/ untouched)
  - Deleting a file: creates a "whiteout" entry in upper/
  - New files: created directly in upper/

--- 6.2 REMBO Sentinel OverlayFS Implementation (Existing) ---

The Sentinel daemon (rembo-sentinel.sh, lines 105-172) already implements
OverlayFS updates:

    apply_overlay_update() {
        local overlay_lower="/system"
        local overlay_upper="$OVERLAY_DIR/upper_${pkg_name}"
        local overlay_work="$OVERLAY_DIR/work_${pkg_name}"
        local overlay_merged="$OVERLAY_DIR/merged_${pkg_name}"

        mkdir -p "$overlay_upper" "$overlay_work" "$overlay_merged"
        unzip -qo "$pkg_file" -d "$overlay_upper"

        # Self-test after applying
        if ! self_test; then
            # Rollback on failure
            rm -rf "$overlay_upper" "$overlay_work" "$overlay_merged"
            blacklist_hash "$pkg_hash" "self_test_failed"
            return 1
        fi
    }

--- 6.4 OverlayFS Mount Script for REMBO_SIDE_PATCH ---

The following script should be placed in the USB root's scripts/ directory
to apply OverlayFS-based overrides at boot time:

#!/system/bin/sh
# 9-rembo-overlay — OverlayFS System Override Script
# Auto-sourced by initrd /init

REMBO_USB="/mnt/$SRC/rembo"
OVERLAY_BASE="/data/rembo-overlay"
OVERLAY_UPPER="$OVERLAY_BASE/upper"
OVERLAY_WORK="$OVERLAY_BASE/work"

apply_rembo_overlay() {
    # Only apply if REMBO overlay data exists on USB
    [ -d "$REMBO_USB/overlay" ] || return 0

    mkdir -p "$OVERLAY_UPPER" "$OVERLAY_WORK"

    # Copy overlay files from USB to data partition
    cp -a "$REMBO_USB/overlay/"* "$OVERLAY_UPPER/"

    # Apply OverlayFS on top of /android/system
    mount -t overlay rembo_overlay \
        -o lowerdir=/android/system,upperdir=$OVERLAY_UPPER,workdir=$OVERLAY_WORK \
        /android/system

    echo "[REMBO-OVERLAY] OverlayFS applied on /android/system"
}

apply_rembo_overlay

--- 8.1 KVM Boot Simulation ---

STATUS: NOT PERFORMED
REASON: The audit environment does not support nested virtualization (KVM).
The VM used for this audit runs on a hypervisor that does not expose
/dev/kvm to guest VMs. Booting the ISO in QEMU/KVM would require:
  - A bare-metal host with Intel VT-x or AMD-V
  - QEMU 8.0+ with UEFI firmware (OVMF)
  - At least 8 GB RAM allocated to guest
  - GPU passthrough or VirGL for graphics

ALTERNATIVE: Complete boot flow was traced via static analysis of the
initrd /init script (454 lines), GRUB config, and Android init process
documentation. The execution path is deterministic and well-documented.

--- 8.2 RTX 4060 Ti Identity Spoofing / 100 Billion Cycle Simulation ---

STATUS: NOT PERFORMED
REASON: Multiple factors make this infeasible:

  1. HARDWARE: No RTX 4060 Ti (AD106) GPU is present in the audit
     environment. GPU identity verification requires physical hardware
     with the target GPU installed.

  2. SCALE: Simulating 100 billion clock cycles at 180Hz would require:
     - 100,000,000,000 cycles ÷ (1,607,000,000 Hz boost clock) = 62.2 seconds
       of real GPU execution time
     - This requires the actual GPU running actual workloads
     - Software-level cycle simulation (e.g., via gem5 or custom RTL) would
       take months of compute time even on a server cluster

  3. GSP FIRMWARE: The GSP (GPU System Processor) firmware loading process
     is handled by the nouveau kernel module using firmware files from
     /system/lib/firmware/nvidia/ad106/gsp/. Race conditions during GSP
     loading would only manifest on real hardware with the actual GPU.

  4. WHAT WAS VERIFIED INSTEAD:
     - GSP firmware file presence and naming (8 binaries confirmed)
     - modinfo nouveau.ko firmware requirements alignment
     - SHA256 integrity between primary and backup firmware paths
     - NVK driver instruction count (18,666 AVX2 in Sovereign build)
     - GRUB boot parameter: nouveau.config=NvGspRm=1

--- 8.3 EDID Spoofing Details ---

The REMBO Stealth Layer mentions EDID spoofing. The init script checks for
writable EDID sysfs entries at /sys/class/drm/card*-*/edid but actual EDID
override requires either:
  - A custom kernel module that intercepts EDID reads
  - A patched nouveau driver with hardcoded EDID data
  - An external EDID override via xrandr (not applicable in Android)

Current implementation: Logging-only (logs available override paths).
The actual EDID spoof is not yet implemented in the codebase.

  - Maintain a rollback snapshot for each overlay change
